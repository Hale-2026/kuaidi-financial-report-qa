## 0. 三步跑通（评审 / 复现用）

```bash
# ① 取代码 + 建虚拟环境（venv 必须先建，见第 3 节的说明）
git clone git@github.com:Hale-2026/kuaidi-financial-report-qa.git
cd kuaidi-financial-report-qa
python3 -m venv .venv
zsh code/bootstrap_deps.sh          # 装依赖 + 功能自检

# ② 拉一次向量模型（96 MB，只需一次；不是 pip 包）
B=https://hf-mirror.com/Xenova/bge-small-zh-v1.5/resolve/main
D=data/model/bge-small-zh-v1.5; mkdir -p $D/onnx
for f in config.json tokenizer.json tokenizer_config.json special_tokens_map.json vocab.txt; do
  curl -sLo $D/$f $B/$f; done
curl -sLo $D/onnx/model.onnx $B/onnx/model.onnx

# ③ 跑完整流程（约 20 分钟：下载 207 MB → 提取切块 → 建索引 → 评测）
zsh run_all.sh
```

跑完直接提问（命令行版，无需启 Web）：

```bash

```

## 3. 环境搭建

**先建虚拟环境，再补依赖（顺序不能反）：**

```bash
git clone git@github.com:Hale-2026/kuaidi-financial-report-qa.git   # 或进入已下载的目录
cd kuaidi-financial-report-qa

python3 -m venv .venv            # ← 必须先建：下面两个脚本都会优先用仓库内的 .venv
zsh code/bootstrap_deps.sh       # 自检 + 补装 + 装完必验
```

> **为什么 venv 必须先建**：两个脚本找 Python 的顺序都是 `$VENV` 环境变量 →
> **仓库内 `.venv`**，且**不写死任何本机 / 个人环境路径**。
> `bootstrap_deps.sh` 只认这两个，找不到就报「找不到虚拟环境」并以退出码 1 中止
> ——**不会**改用系统 Python（否则依赖会被装成全局包，污染本机）；
> `run_all.sh` 在两者都缺时才会退回系统 `python3` 跑自检，而系统 Python 一般没有
> 这些依赖，第 0 步同样会中止并提示你先建 `.venv`。
> 想用已有的 conda / 其他 venv，设 `VENV=/path/to/env` 再跑即可。

脚本干三件事：① 常规依赖（有 wheel）整批直装，装完**逐个 import 复检、缺谁单独
补装**（不让一个包失败连累其他包）；② `jieba` / `zhconv` 这类**只有
sdist** 的包单独处理，pip 装不上就自动走「下源码包 → 手工解包 → 拷进 site-packages」；
③ 收尾做**功能性自检**（zhconv 要真能把「單票收入與毛利率」转成简体才算过，
光 import 成功不算；向量模型文件也在此校验）。

手工等价命令：

```bash
python3 -m venv .venv
zsh code/bootstrap_deps.sh       # 一步到位，推荐
```

> ⚠️ **别只跑 `.venv/bin/pip install -r code/requirements.txt`。** 清单里的
> `jieba` / `zhconv` 在 PyPI 上只有 sdist 源码包，本机 pip 解包会报 `EEXIST`
> （见下方「已知坑 1」）；**而且这条报错会让整条 pip 命令 abort —— 同一批里
> 其他包也会一个都装不上**。`bootstrap_deps.sh` 已把这两个包从整批里拎出来
> 单独处理，直接用脚本即可。

**已知坑 1 —— pip 解包纯 sdist 包会报错，且会连累整批：** 本机 pip 解包
`jieba`、`zhconv` 时报
`EEXIST: file already exists, mkdir .../pip-install-*/jieba_xxxx`
（换 `TMPDIR`、加 `--no-cache-dir` 均无效）。这两个包是纯 Python，手工装即可：
下载 tarball → `tar -xzf` → 把包目录拷进 `site-packages/`
（`bootstrap_deps.sh` 已自动化这一步）。
**注意这个报错的杀伤范围**：它会让整条 pip 命令直接 abort。所以
`bootstrap_deps.sh` 的 1/4 批**只放有 wheel 的包**，装完还逐个 import 复检、
缺谁单独补装——避免一个 sdist 包把另外 12 个包一起带崩。

**已知坑 2 —— jieba 缺席不该让整条流水线崩：** `03_build_index.py` 把 jieba 当
**可选依赖**处理：装了就用地道分词 + 领域词典；没装会自动降级为**内置 CJK 二元
切分 + 领域词命中**（BM25 照常可用，只是分词精度略降）。
`rank_bm25`（→ 自实现 BM25）、`sklearn`（→ 仅影响兜底向量）同样各有降级路径。
真正的**必需依赖**只有：
`pymupdf / numpy / onnxruntime / tokenizers / requests / tqdm /
flask / zhconv / markdown`（完整清单见 `code/requirements.txt`；
清单已与代码逐条 `import` 核对过，不含未使用的包）。

**向量模型：** 从 hf-mirror 拉 BGE-small-zh-v1.5 的 ONNX 版（96 MB，CPU 推理，
不依赖 torch，避免装 2 GB 的深度学习栈）：

```bash
B=https://hf-mirror.com/Xenova/bge-small-zh-v1.5/resolve/main
D=data/model/bge-small-zh-v1.5
mkdir -p $D/onnx
for f in config.json tokenizer.json tokenizer_config.json special_tokens_map.json vocab.txt; do
  curl -sLo $D/$f $B/$f; done
curl -sLo $D/onnx/model.onnx $B/onnx/model.onnx
```

下完后的目录必须长这样（`run_all.sh` 的 0/7 自检就是按这两条路径找的，
tokenizer 在**模型根目录**、模型文件在 **onnx/ 子目录**，放错位置会报"缺向量模型"）：

```
data/model/bge-small-zh-v1.5/
├── config.json            tokenizer.json
├── tokenizer_config.json  special_tokens_map.json
├── vocab.txt
└── onnx/model.onnx
```

**一键跑全流程（幂等，可反复执行）：**

```bash
cd kuaidi-financial-report-qa    # 进入本仓库根目录（= clone 出来的目录名）
zsh run_all.sh
```

`run_all.sh` 的 0/8 步会自检依赖：缺了就自动调 `bootstrap_deps.sh` 补装，
补完仍缺则**直接中止**（避免白跑一遍 20 分钟的提取）。

## 6. 关键设计决策

### 6.1 表格按行列还原（而不是当纯文本堆着）

`page.find_tables()` 拿到表格网格后，做两步清洗：

1. **单元格内换行直接拼接**。中文财报表格的单元格换行绝大多数是排版折行：
   - `归属于上市公\n司股东的净利\n润（元）` → `归属于上市公司股东的净利润（元）`
   - `25,084,468,028\n.72` → `25,084,468,028.72`
     （不这样处理，数字会被打成 `25,084,468,028 .72`，数值问答直接崩）
2. **删掉整列为空的列**。合并单元格会让 5 列表被还原成 19 列，噪声极大。

表格块渲染成 Markdown 管道表，且在切块时**整表成块、绝不从中间切断**。

### 6.2 切块带「公司 / 章节 / 页码」

- 正文按 `第X节` 识别章节（限定出现在页面顶部、节号单调不减，以排除目录页）；
  港股报告无「第X节」体例，另用已知标题词表识别（管理层讨论与分析、财务报表附注…）
- 页眉页脚按「跨页高频重复行 + 纯页码行」剔除
- 段内按句末边界累积到约 700 字，相邻块重叠约 100 字
- 每个块携带：`公司 / 代码 / 交易所 / 细分行业 / 报告类型 / 章节 / 页码区间 / 是否表格`

### 6.3 双索引与融合

- **BM25（词法）**：jieba 分词 + 金融/快递领域自定义词
  （单票收入、中转、加盟商、扣非净利润…），擅长精确术语与数字
- **向量（语义）**：bge-small-zh-v1.5 句向量，[CLS] 池化 + L2 归一化，
  查询侧加官方检索指令；擅长「价格战怎么体现」这类没有字面重合的问题
- **融合**：RRF（Reciprocal Rank Fusion，k=60），对两路排名取调和，
  不需要调分数权重 —— 也便于在页面上直接对比三种模式的表现差异

### 6.4 答案生成走「抽取式」

不引入大模型，而是从召回块中按「查询词命中密度 + 数字命中 + 位置」挑句子，
拼成答案并**逐句挂出处**。理由：本作业的核心是评测**检索**质量，
生成式模型会把检索失败「圆过去」，掩盖问题；抽取式可复现、可审计，
每一句都能点回原始页码。代码同时留了 OpenAI 兼容接口的开关
（把 `OPENAI_BASE_URL` / `OPENAI_API_KEY` 写进 `.env` 即自动切换为 grounded 生成 ——
`04_ask.py` 顶层有个零依赖的 `load_dotenv()` 读取仓库根目录的 `.env`；
已存在的真实环境变量优先，不会被文件里的值覆盖。`.env` 已在 `.gitignore` 中排除，
仓库里只留不含真实值的 `.env.example` 模板；源码里没有任何 key，也不会出现在提交里）。

跨公司题另做一层**按公司轮转 + 指标词优先**的答案拼装：否则同一家公司的高分句
会把 6 个位置占满（实测未处理前，Q01 的答案里圆通给的是"营业收入 386.21 亿"，
韵达却给成了"业务量 122.57 亿票"、顺丰给成了"营业成本 1,345.9 亿"）。

### 6.5 分组召回（cover 模式）—— 专治跨公司全景题

问题里点名多家公司时，单轮全局检索必然翻车：**BM25 会把「释义表」「子公司名录」
这类把公司名罗列几十遍的附录表顶到最前面**（实测圆通第八节子公司名录表逐行都是
"XX圆通速递有限公司"），Top-5 被一家公司刷屏，其它公司根本进不来。

cover 模式的做法：

1. 识别问题里点名的公司（全称 + 简称表）；
2. **剔除公司名**构建子查询（否则 BM25 继续被释义表刷屏）；
3. 对每家公司**独立检索**，组内用「指标焦点词」硬过滤，噪声块直接挡掉；
4. 各公司的结果**轮转交错合并**（而不是按公司分块），保证 Top-5 每家都有位置；
5. 不够再用全局结果补足。

两个容易踩的细节：
- 焦点词**只从指标术语表取**，绝不按 IDF 挑 —— IDF 会选中"多少""差距"
  这类财报里罕见但零信息量的疑问词；
- 同义组要**整组带出**（单票收入 / 票均收入 / 包裹单价 / 每票收入），
  否则中通那份报告里根本没有"单票收入"三个字，硬过滤会把它的候选全部清空。

### 6.6 跨市场术语同义扩写

同一个指标各家披露用词不同，查询里出现任一变体就把同组其它变体加进 BM25 词袋：

| 指标 | 顺丰（A 股） | 中通（港股） |
|---|---|---|
| 单票收入 | **票均收入** 14.4 元/票，同比 +3.3% | **包裹单价** 增加 12.0% |

不扩写的话，问"中通和顺丰的单票收入"两路都搜不到 —— 这正是"跨市场口径对齐"
这道题的考点本身。这几个跨市场术语也补进了 jieba 领域词典（57 → 62 词）并重建
BM25 索引，否则"包裹单价"会被切分成"包裹/单价"，词元层面依然对不上。

## 6.7 评测口径：召回层 / 答案层两层，且失败要定位到「哪一项义务」

这一节是本项目的评测方法论，**不是**「跑一下看命中率」那种做法。

### 为什么不能只评 Top-5 关键词命中

「关键词组在 Top-5 块里出现了」是**宽松上界**，它回答的是「证据召回到了没」，
回答不了老师提的两个问题：**答案实际对不对？错的话错在哪一项？**
具体有三类漏判：

1. **数值无归宿**：块里出现了 `4,026,356.42 万元`，但没说清是**谁的、哪个口径、哪一期**
   —— 关键词命中会判它「命中」，可答案其实不可用。
2. **召回到了但没答出来**：证据在 Top-5 里，答案拼装时被别的高分句挤掉 ——
   召回层满分、答案层零分。
3. **该说「没有」的时候说了数字**：语料里根本没有该口径，系统却编了一个
   —— 关键词命中判「未命中」，但这恰恰是**最该被表扬**的正确行为（系统没编）。

### 两层口径（依据课程第三课 P90–P92）

| 层 | 判什么 | 数据来源 | 读法 |
|---|---|---|---|
| **召回层** | 证据组是否被召回（同义写法组命中） | `hits[:5]` 的正文 + 块元数据 | 宽松上界，「证据全部召回」 |
| **答案层** | 证据义务是否被**最终答案**覆盖 | `answer` + `bullets`（含角标归属） | 严口径，「真的答出来了」 |

**答案层的判定单位是「证据义务」**（`code/eval_questions.json` 里每题一个
`obligations` 列表，共 10 题 **42 项**）。一项义务 = `主体公司 + 指标 + 期次 + 标准值 + 出处页码`。
逐项判定三种状态：

- **已覆盖**：该数值出现 **且 归宿正确**（数值必须落在该主体公司自己的报告块 / 角标里）；
- **部分**：数值出现了，但没归到对应公司 —— 这就是 P91 说的「数字丢口径」；
- **缺**：数值根本没出现。

> 数值「归宿正确」这一条是刻意的严格：`values` 是子串匹配（匹配前会去掉千分位逗号与空白），
> 但匹配到的是**谁的**必须对得上。归属判定走三条路径：① 块/角标的公司 = 义务主体；
> ② 该义务本身就是跨公司结论（`subject` 为空）；③ 答案正文自己写了公司名。

### 问题形状先分类（课程 P90 第一步：「第一步不是搜索，是判断问题的形状」）

| 形状 | 含义 | 本作业 | 典型考点 |
|---|---|---|---|
| 局部 | 单公司单指标 | Q04–Q09 | 定向召回是否干净 |
| 全局·全景 | 跨公司汇总 | Q01、Q02、Q10 | 没有哪一块能单独回答（P61–P63） |
| 多跳 | 对比 + 归因 | Q03 | 跨市场口径不可直接相减 |

### 失败归因：缺的那一项，到底缺在哪（8 类）

台账第 3 节会把「答案层缺掉的每一项义务」自动归到下面某一类。
判定顺序刻意**从「与检索无关」排到「检索侧」**，避免把数据边界误记成检索失败：

| 代码 | 归因 | 怎么判出来的 |
|---|---|---|
| A | 语料未披露该口径 | 全语料（含过滤器范围）搜不到该数值 → 数据边界，系统明说「未披露」是**正确行为** |
| B | 公司名漏识别 | 题面点名的公司没被 `detect_companies` 认出 → 分组召回分不出这一组 |
| C | 焦点词误杀 | **消融实证**：`focus_off=True` 关掉 cover 的指标焦点词硬过滤后，该项立刻可召回 |
| D | 召回不足 | 语料里有、也没被误杀，但 Top-K 没排进来（**责任在检索侧**） |
| E | 口径不一致 | 该公司的披露用词与题干关键词组完全不重合 |
| F | 数值无归宿 | 数字召回到了，却没归到对应公司（P91「数字丢口径」） |
| G | 语料表格未抽取（**本项目的缺陷**） | 报告里确实写了，但切块时表格只剩表头、单元格为空 → 检索侧的真实失败，**不计入数据边界** |
| H | 答案未取到已召回的证据（**责任在答案侧**） | 含该数值的块**已召回（Top8 覆盖该项义务）**，但选句/拼句没把那条证据取出来 |

> **A 与 G 必须分开读。** A 是「报告本身就没写这个口径」（例：中通 2026 半年报
> 通篇没有『市场份额/市占率/市场占有率』）；G 是「报告写了、我们没抽出来」
> （例：申通 P25 分行业表的『毛利率』列只剩表头，回原始 PDF 第 25 页可读到
> 「快递服务 6.97%、增加 2.08 个百分点」）。把 G 说成 A 就等于替自己的流水线开脱。
>
> **H 与 D 也必须分开读。** 两者都是「最终答案里没有这个数」，但责任方不同：
> D 是检索侧没把块排进 Top-K；H 是**块已经召回到了、答案组装却没取出来**。
> 判据可复核 —— 答案生成读的正是 Top8 召回块，所以「Top8 已覆盖但答案未覆盖」
> 就是答案侧的失误。实例 Q07-1（极兔速递全球处理包裹量 175.0 亿个，bm25 模式）：
> Top8 召回已覆盖，但答案挑的是中国区收入 / 单票收入 / 跨境收入那几句，
> 175.0 没进答案。**只看 D 会把答案侧的缺陷误记成检索失败** —— 这正是加入 H 的意义。
> （H 共 13 项：Q06/Q07/Q10 的部分义务在 hybrid / bm25 / vector 下命中此因；
> cover 模式同类缺口若经 `focus_off` 消融可召回，则优先判 C。）
>
> **C 是真消融，不是推测**：cover 模式的「指标焦点词硬过滤」可能把正确块挡掉，
> 于是评测脚本对每个未覆盖项**实际重跑一遍 `focus_off=True` 的检索**，
> 只要能召回来就判 C —— 这是一次可复现的对照实验。

### 全景题必须逐公司取证（课程 P61–P63）

P63 的原话是「五个回答同样只覆盖几家，**哪个路线都只看到其中一角**」。
所以对 `shape = 全局` 的题，台账第 4 节会**按公司逐家列出**：
该公司名有没有被识别、对它列了几项义务、覆盖了几项、缺的是哪一项。
本作业的 Q02 横跨 7 家公司，`obligations` 有 8 项 —— 已超过 P92 建议的
「最多 6 项」上限。这不是设计失误：全景题的义务数天然 ≥ 公司数，
**工程上的对策是「按公司分组取证」而不是一次性追求 8 项全中**，
 这也正是 cover 模式（分组召回）存在的理由。

| | 本表「首轮实测」列 | 台账「v1 判卷口径」列 |
|---|---|---|
| 检索侧 | 首轮版本（词典未补跨市场术语、无分组召回） | **当前版本** |
| 判卷侧 | 首轮规则（仅正文、不含块元数据） | 同一套首轮规则（仅正文） |
| 性质 | **历史实测**，固化记录，不由脚本重算 | 用当前检索结果**重算**得出 |
| hybrid / bm25 | 60% / 70% | 70% / 80% |

差的正好是 **Q03**（中通 vs 顺丰单票收入）：领域词典补入「票均收入 / 包裹单价」
并重建 BM25 后，该题由未命中转为命中，hybrid 与 bm25 各 +1 题，即 +10pt。
台账第 1 节已把这三个量**并列成列**（外加一栏逐模式差异来源），可直接对照。

### 7.2 答案层：召回到了 ≠ 答出来了（本作业的主口径）

依据课程第三课 P90–P92：先把问题拆成**证据义务**，逐项判 已覆盖 / 部分 / 缺；
数值必须**归宿正确**（是谁的、哪个口径、哪一期）才算覆盖。

| 路线 | 召回层：证据组命中@Top5 | 召回层：义务覆盖@Top5 | 召回层：义务覆盖@Top8 | **答案层：义务覆盖（最终答案）** | 义务总数 |
|---|---|---|---|---|---|
| BM25（仅词法） | 90% | 43% | 48% | **36%** | 42 |
| 向量（仅语义） | 80% | 36% | 43% | **33%** | 42 |
| RRF 融合 hybrid | 90% | 43% | 50% | **40%** | 42 |
| **分组召回 cover** | **100%** | 50% | **64%** | **52%** | 42 |

> **四列不是同一个量，逐列变严。** 答案生成读取 Top8 召回块，所以与答案层直接可比
> 的是**第 3 列（召回层：义务覆盖@Top8）**：cover 的答案层 52% 对应此列的 64%，
> 落差 12pt 就是「召回得到、答不出来」的损耗；hybrid / bm25 的答案层已与自身
> 该列基本持平。
> 这条落差正是老师指出的「Top5 关键词命中不能替代答题正确」。

### 7.3 按问题形状分（cover 路线；课程 P90 第一步）

| 问题形状 | 题数 | 义务数 | 召回@Top5 | 召回@Top8 | 答案层 |
|---|---|---|---|---|---|
| 局部（单公司单指标） | 6 | 20 | 65% | 75% | **65%** |
| 全局·全景（跨公司） | 3 | 19 | 32% | 53% | **37%** |
| 多跳（对比 + 归因） | 1 | 3 | 67% | 67% | **67%** |

读出两件事：① **全景题的召回明显弱于局部题**（32% vs 65%），这正是课程 P61–P63
说的「全景题没有哪一块能单独回答，哪条路线都只看到其中一角」；② 局部题的答案层
已追平召回层，说明单公司题「召回到就能答对」，**损耗几乎全部发生在跨公司题上**。

### 7.4 失败归因分布（cover 路线，答案层未覆盖项）

| 代码 | 归因 | 次数 | 读法 |
|---|---|---|---|
| A | 语料未披露该口径 | 16 | **数据边界，不是失败**（P92：缺数据的明说、不许编） |
| C | 焦点词误杀 | 4 | cover 特有，已用 `focus_off` 消融实证 |
| D | 召回不足 | 63 | 语料里有、也没被误杀，但没排进 Top-K（**检索侧**） |
| E | 口径不一致 | 0 | — |
| F | 数值无归宿 | 0 | — |
| G | 语料表格未抽取（**本项目缺陷**） | 4 | 申通 P25 分行业表毛利率列被误判成表头 |
| H | 答案未取到已召回的证据（**答案侧**） | 13 | 块已在 Top8 召回，但答案选句没取到数（如 Q07-1 极兔全球包裹量 175.0 亿个） |

（计数按 `(题目, 模式, 义务)` 三元组；完整清单见 `output/eval_table.md` 第 3 节。）
**D 与 H 的分界**：答案生成读 Top8，所以「Top8 已覆盖、答案未覆盖」= H（答案侧），
其余才是 D（检索侧）。加入 H 之前这 13 项被并进 D，会把答案侧缺陷误记成检索失败。

**判卷口径修正（三处，都是评测工具的缺陷而非系统缺陷）：**

1. **命中判定纳入元数据**：公司名本来就由 `companies` 过滤器强约束，
   再要求正文复述一遍会把正确召回判成失败（Q02 的 Top1 正是顺丰毛利率原文，
   只是正文里没写"顺丰"三个字）。
2. **区分「检索失败」与「语料未披露」**：Q09 问中通"市场份额"，
   全语料核查确认中通 2026 半年报未按该口径披露（该词仅出现在 2025 年报的
   风险提示里，属定性表述）。系统找不到、且**没有编造数字**，属正确行为；
   故降为 soft 组单列，不判失败。
3. **答案层的句子切分与选句**：抽取式答案原先按「。；！？」切句，把
   「单票收入2.17元；单票成本1.90元；单票毛利0.27元」这类**同一口径的并列分句**
   切成三句，摘要只能抢到一句 —— 三个数只答出一个。改为**只按「。！？」切句**，
   并给「含数字 + 含问题指标词」的句子加重（P91：数字要带口径）。
   实测 cover 路线答案层覆盖由 38% 提升到 **52%**，Q08 由 0/3 转 3/3。

### 7.5 逐题答案判定书：40 份实际作答，逐份判「正确 / 部分正确 / 错误」

课件 P61–63、P90–92 的落地要求是**分开评价证据覆盖与答案表现**，并
**保存真实答复、逐题给出判定理由**。为此新增 `code/06_answer_audit.py`，
把 `output/eval_runs.json` 里 **40 份系统实际作答的原文**逐份摊开，产出两份：

- **`output/作业3A_10题实际作答与判定.pdf`（14 页）** —— 一题一页的**提交件**：
  实际答复 + 网页证据卡片（含数值与页码）+ 四路线判定 + 判定理由 + 全景题逐公司取证；
- `output/作业3A_逐题答案判定书.pdf`（77 页）+ `output/逐题实际答复存档.md`
  —— 每题 4 条路线的完整作答原文与逐项覆盖明细，**留档备查**（不进提交附件）。

- **判定规则**：`正确` = 该题义务全部覆盖；`部分正确` = 覆盖 1 项以上但不满；`错误` = 0 项。
  「覆盖」= 标准答案的数值出现在答复中，**且**归属到正确的公司 / 口径 / 期次。
- **每份作答记录**：答复原文 → 判定 → 判定理由 → 证据覆盖逐项（标准数值 + 出处页码）
  → 答复引用的证据（公司 · 报告期 · 章节 · 页码 · 块 ID）。

**结果（40 份作答）：正确 7 · 部分正确 28 · 错误 5。**

**缺口集中在跨公司全景题** —— 四条路线各自只覆盖其中几家，都只看到一角。

### 7.6 一页结论：课程 P163 要求的是「一页」，严格压到 1 页

第三课 P163 对 A 方向的交付要求是「**代码仓库 + 页面截图 + 一页结论（哪类题答得好、
哪类翻车、为什么）**」。此前 `output/一页结论.pdf` 由详版 Markdown 直接打印，实际
**4 页**，不符合「一页」。现新增 `code/07_one_pager.py`：

- 正文只保留老师点名要的几块：**主要对照结果**（4 路线 × 召回层 / 答案层）·
  **哪类题答得好、哪类翻车**（按问题形状）· **全景覆盖**（Q01 / Q02 逐公司取证）·
  **方法局限**（诚实清单）；
- 数字**全部从 `eval_scores.json` / `eval_runs.json` 现算**，不手写、不复制旧文档，
  保证与 `eval_table.md` 逐格对得上；
- 渲染后**用 pymupdf 实测页数**：>1 页就自动降字号重排，仍超则**报错退出**
  （不静默交一份超页文件）。实测输出 **1 页（10.8pt）**；
- 详版结论不再打印成 PDF，改为**正式报告的「第一部分 · 结论（详版）」**；
  `code/make_report.py` 已不再生成 `output/一页结论.pdf`，避免把它覆盖回 4 页。
- 该 PDF **同时提交进公开仓库根目录**（`一页结论.pdf`）—— 老师复核时核的是**公开仓库**，
  只做成附件等于没交；`run_all.sh` 的 **7/8 步会自动同步这份副本**（`output/` 被忽略、
  根目录不被忽略），下次重跑同样入库。

## 8. 已知限制

1. **合并单元格的跨行项目名**无法完全还原 —— 项目名被拆到多行时，
   表格首列可能只保留第一行文字。
2. **扫描件/图片型表格**（少数港股文件的内嵌图片）无法提取，`find_tables` 会跳过。
3. 沪市公司依赖巨潮（上交所接口在本机网络不可达）；巨潮对**高频请求**有限流，
   脚本已加退避重试，但首次全量下载仍可能需要重跑一次。
4. 向量模型是 512 维小模型，语义召回上限有限；财务表格类问题主要靠 BM25 + 表格块。
5. **两层口径仍有各自的天花板**：召回层是宽松上界；答案层把「数值 + 归宿 + 期次」
   一起判，能卡住「数字丢口径」和「召回到了没答出来」，但它判的是
   **证据义务是否被覆盖**，仍**不等于自然语言答案的语义正确性**——
   例如「顺丰最高」这句话的推理是否正确、因果解释是否成立，机器只做了
   数值-归属核对，最终仍需人工读一遍。台账第 2 节每题都附了 cover 模式的完整
   答案与出处，就是留给人工复核的。
6. **双栏排版的句子串行**：顺丰那份报告是双栏排版，抽取式答案偶有跨栏拼接
   （需版面分析才能根治）。
7. 样本量小：每类题型只有 1 道题，单题成败会被放大成 0%/100%。
8. **表格抽取存在缺口（归因代码 G，已定位到具体一处）**：
   申通快递 2026 半年报 P25「占公司营业收入或营业利润 10% 以上的行业情况」表，
   切块后**只剩表头、单元格数值为空**（原文可读到「快递服务 32,065,895,724.63 /
   29,831,075,422.74 / 毛利率 6.97 / 增加 2.08 个百分点」）。
   根因是这张表的表头跨多行合并（`毛利率\n（%）`、`营业成本比\n上年同期增\n减（%）`），
   行列还原时把数值行也一并判成了表头。影响面：10 题 42 项义务里命中 1 项
   （Q02-4 申通毛利率），已在台账里单列为 G 而不是含糊地算进「语料未披露」。
   **这与中通『市场份额』那类「报告本身没披露」是两回事**——A 是数据边界，
   G 是本流水线的缺陷；README 第 6.7 节与台账第 3 节都对二者做了区分。

**已知坑 3 —— 受限环境里 Chrome 无头截图会 FATAL：** 在沙箱/CI/远程会话中，
Chrome 自带 sandbox 初始化失败（`Failed to initialize sandbox: Operation not
permitted`），GPU 进程退出后直接 FATAL。`code/shot.sh` 已固定加 `--no-sandbox`
与 `--disable-dev-shm-usage`，本地与受限环境都能截图。
